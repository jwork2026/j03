# 葫芦娃阵型作业

这是一个用 Java 编写的面向对象建模示例，在 j02 葫芦娃排序的世界观上扩展到二维战场。

运行 `make` 可以编译并运行当前示例：

```shell
make
```

当前实现：老爷爷指挥七个葫芦娃摆出长蛇阵，蛇精率领小妖摆出鹤翼阵，对峙后进入回合制交战——每回合双方战术各自读取战场，为本方每个成员重新决策动作（移动或攻击），全军行动；首领被击退的一方落败，胜负由双方战术的对抗涌现而来。战场只允许生物走到相邻的空格子（禁止“瞬移”）。自带一个简化的游戏引擎（`GameEngine` + `Renderer`），在终端里逐帧播放摆阵过程。

## 作业要求

1. 仔细阅读代码，理解其继承层次与阵型抽象，指出其中不合理的设计之处并改正（提示：留意重复的代码与 `instanceof` 的使用）。

2. 新增至少两种阵型（如八卦阵、方阵、雁行阵等），要求**不修改**现有指挥与战场代码，仅通过新增 `Formation` 子类完成。

3. 两个阵营在同一战场上布阵时可能发生位置冲突。请设计冲突的检测与处理方式（如报告冲突、调整锚点或重新规划）；并支持“变阵”：已经就位的队伍从一种阵型变换到另一种阵型，变换过程中每个生物只允许移动到相邻（上下左右）的空格子，变阵过程要通过 `GameEngine` 逐帧展示。

4. 新增至少一种战术（如各个击破、围魏救赵、且战且退），要求不修改 `Battle` 的回合循环，仅通过新增 `Tactic` 实现类完成；让不同的战术组合对战，在 `REPORT.md` 中记录并分析结果。想一想：阵型可以一次性产出完整计划（`FormationPlan`），战术为什么必须逐回合重新决策？

## 思考题（不计分，写入 `REPORT.md` 可加分）

- 内置的贪心走位（`CaptureLeaderTactic.stepTowards`）遇到障碍会绕路失败甚至僵住。如何把��寻路”从战术中抽象出来，让所有战术共享更聪明的走位？
- `Camp` 用了枚举而 `Huluwa` 没有。`Huluwa` 能否也改为枚举？需要对现有继承层次付出什么设计代价？
